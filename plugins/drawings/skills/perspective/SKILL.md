name: perspective
description: Chooses pedestrian-level viewpoints in a design and draws each as an accurate eye-level base view from the massing, with the existing buildings, vegetation, streets, rail, water and terrain around it, then renders each with an image model when a key is there, keeping its geometry. Use when asked for perspectives, eye-level views, street views, or spatial representations of a design.

# Perspective

Reads: massing, streets, open-space, ground-floor, drawing-graphics, narrative, panel-layout

Inputs: `massing/massing.geojson` in the proposal folder, the project's site folder, `narrative/narrative.md` for what the views should tell, the brief for how many views it asks for, `drawing-graphics/standard.md` for the look, `streets/streets.geojson` for the street surface and `open-space/open-space.geojson` for its trees, when they exist. Never invent data: with no massing, stop and say so; everything else that's missing goes in `assumptions.md`. Work in the proposal folder you're told, else the newest in the project's `proposals/`, else a new `<YYYY-MM-DD>_draft/`, and write only into its `perspective/`.

Run `python "${CLAUDE_SKILL_DIR}/scripts/perspective.py" <proposal folder> --count N`, with N the number of views you read in the brief, in whatever language it is, or the number of view frames in `panel-layout/layout.json`, each chosen to show what its `shows` asks; without `--count` it makes two and warns. Needs `pip install shapely pyproj numpy requests`, and Chrome or Edge. The site folder is found next to `proposals/` or through the project's `CLAUDE.md`; else pass `--site`. Terrain comes from `terrain.csv` (columns `lon, lat, ele`) in the site folder, else from a free open elevation service, sending only coordinates; if neither works the ground is flat and the summary says so. The tones come from `drawing-graphics/style.json`. Pass any corrected assumption in a JSON file with `--options`, and under its `style` only a tone to override (the keys are `STYLE` in `scripts/draw_view.py`, line weights and the tones of `views_map` too).

Then check the result; the script can't. Open `views_map.png` and every `_base.png`: does each view show what the narrative needs? A view should read as buildings, public space, landscape and human scale together, with nothing blocking the eye. If not, change the view count or redraw edited cameras with `--views views.json`, and say why in `summary.md`. A view shows whatever the data shows, so read every warning: a warning you can't resolve stays in the summary. Then the facades. First look for the team's latest word on facades: `git fetch` and the commits since the last run, the open issues (`gh issue list`, `gh pr list`) and the project's feedback folder, for anything on facades, windows, openings, glazing or materials. Such an instruction overrides `${CLAUDE_SKILL_DIR}/facades.json`, which is a provisional design proposal, not a team decision: write the instruction into `perspective/facades_override.json` (the same keys; `by_type` names a system per massing `type`, `systems` gives each its opening width, sill, head and rail) and name its source in `summary.md`; with none, keep the proposal and say so. Then run `python "${CLAUDE_SKILL_DIR}/scripts/facades.py" <proposal folder> --site <the same site folder>`: two languages, floor-to-ceiling glazing or one long horizontal window per bay, one per building, the same on every floor and bay, ground floor included, on the 3 m bay, with doors from `ground-floor/*.geojson`; it keeps the plain view as `view-N_plain.svg/png`, redraws `view-N_base.svg/png` with the facades and writes `facades_drawn.json`. Never present the facades as agreed by the team unless an instruction says so. Then render: `python "${CLAUDE_SKILL_DIR}/scripts/render.py" <proposal folder>` sends each `_base.png` and `_depth.png` to Gemini with a prompt from the view's reason, the narrative's idea, the style (`render_style` in `style.json`, else an illustrated default: line drawing with flat colour, not a photograph), the render section of `standard.md` (else pass its look as `look` in `--options`) and an order to keep the geometry, writes `<view>.png` and `render.json`, and warns if a size differs. Needs `pip install google-genai pillow python-dotenv` and `GEMINI_API_KEY` in the project's `.env`, or, with no Gemini key, `REPLICATE_API_TOKEN` there for the same model on Replicate (`--provider replicate`); `--references IMAGE ...` sends the project's style references after the base and depth (only read, never copied into the image); without them it stops with one line and no image, so say in `summary.md` that the views are unrendered. Look at each `<view>.png` once beside its `_base.png` and name in `summary.md` anything the image changed: a building added, moved or gone, another horizon.

Large, a view is judged on its floors and its edges; small, on its one spatial idea, so keep each view's subject simple. A perspective has no scale: never give one in `summary.md`. Trees are drawn as elevation trees, each at its own crown: a wavy crown in one of five greens of the standard's, shaded on one side, a tapering trunk that forks into two branches inside the crown.

**What it writes:** `view-N_base.svg` and `.png`, `view-N_depth.png`, `view-N_ids.png` (what each pixel is), `view-N.png` and `render.json` (each prompt and model) when rendered, `view-N_stale.png` for a render whose base a later run redrew otherwise, `views_map.svg` and `.png`, `views.json` (each camera, why it was chosen, its scores), `candidates.csv` (not on a `--views` redraw, which leaves any earlier one as it was), `building_status.csv`, `terrain.csv` if fetched, `assumptions.md`, and `summary.md` in three lines: the views, how many from how many candidates, what you're unsure of. With a massing marked `"standin": true`, or a proposal folder named `test`, the view files and `views_map` start with `TEST_`, the other files keep their names, and the summary says so.
