# Perspective

Reads: massing, streets, drawing-graphics, narrative, panel-layout

Inputs: `massing/massing.geojson` in the proposal folder, the project's site folder, `narrative/narrative.md` for what the views should tell, the brief for how many views it asks for, `drawing-graphics/standard.md` for the look, and `streets/streets.geojson` for the street surface when it exists. Never invent data: with no massing, stop and say so; everything else that's missing goes in `assumptions.md`. Work in the proposal folder you're told, else the newest in the project's `proposals/`, else a new `<YYYY-MM-DD>_draft/`, and write only into its `perspective/`.

Run `python "${CLAUDE_SKILL_DIR}/scripts/perspective.py" <proposal folder> --count N`, with N the number of views you read in the brief, in whatever language it is, or the number of view frames in `panel-layout/layout.json`, each chosen to show what its `shows` asks; without `--count` it makes two and warns. Needs `pip install shapely pyproj numpy requests`, and Chrome or Edge. The site folder is found next to `proposals/` or through the project's `CLAUDE.md`; else pass `--site`. Terrain comes from `terrain.csv` (columns `lon, lat, ele`) in the site folder, else from a free open elevation service, sending only coordinates; if neither works the ground is flat and the summary says so. The script doesn't read `standard.md`: to follow it, put its tones in a JSON file under `style` (the keys are `STYLE` in `scripts/draw_view.py`), and pass any corrected assumption in the same file, with `--options`. Line weights and the tones of `views_map` are `STYLE` keys too.

Then check the result; the script can't. Open `views_map.png` and every `_base.png`: does each view show what the narrative needs? A view should read as buildings, public space, landscape and human scale together, with nothing blocking the eye. If not, change the view count or redraw edited cameras with `--views views.json`, and say why in `summary.md`. A view shows whatever the data shows, so read every warning: a warning you can't resolve stays in the summary. Then render: `python "${CLAUDE_SKILL_DIR}/scripts/render.py" <proposal folder>` sends each `_base.png` and `_depth.png` to Gemini with a prompt from the view's reason, the narrative's idea, the style (`render_style` in `style.json`, else an illustrated default: line drawing with flat colour, not a photograph), the render section of `standard.md` (else pass its look as `look` in `--options`) and an order to keep the geometry, writes `<view>.png` and `render.json`, and warns if a size differs. Needs `pip install google-genai pillow python-dotenv` and `GEMINI_API_KEY` in the project's `.env`; without them it stops with one line and no image, so say in `summary.md` that the views are unrendered. Look at each `<view>.png` once beside its `_base.png` and name in `summary.md` anything the image changed: a building added, moved or gone, another horizon.

Large, a view is judged on its floors and its edges; small, on its one spatial idea, so keep each view's subject simple. A perspective has no scale: never give one in `summary.md`.

**What it writes:** `view-N_base.svg` and `.png`, `view-N_depth.png`, `view-N_ids.png` (what each pixel is), `view-N.png` and `render.json` (each prompt and model) when rendered, `view-N_stale.png` for a render whose base a later run redrew otherwise, `views_map.svg` and `.png`, `views.json` (each camera, why it was chosen, its scores), `candidates.csv` (not on a `--views` redraw, which leaves any earlier one as it was), `building_status.csv`, `terrain.csv` if fetched, `assumptions.md`, and `summary.md` in three lines: the views, how many from how many candidates, what you're unsure of. With a massing marked `"standin": true`, or a proposal folder named `test`, the view files and `views_map` start with `TEST_`, the other files keep their names, and the summary says so.
